# Standalone Windows native-premises check

This bounded driver targets **only**
`8d727a4c74808cf9785c764e87c45bf264c6f822`. Its own driver revision is recorded
separately. CI builds Rust **1.98.1 MSVC x64 with static CRT**; the operator needs
no Rust, Visual Studio, Git for Windows, Python, or helper script.

The workflow runs only on pushes to `ci/windows-native-check`. It waits for the
existing runtime producer **42120608528**, verifies its successful main head
`006b30f02a3c9cec61f8f3cc32fde6b0d248fc34`, and downloads only
`bridge-windows-runtime-006b30f02a3c9cec61f8f3cc32fde6b0d248fc34-1`.
It never dispatches that producer or rebuilds QEMU.

Both actual producer ZIPs are independently verified against unchanged external
producer locks before runtime extraction. The trusted pin contains every actual
runtime ZIP entry, including `provenance/runtime-manifest.json` itself.
Authentication comes from selecting the known producer through authenticated
GitHub download, not from self-described JSON or hashes. This is not remote
attestation or proof of binary-to-source equivalence.

## What the check means

On the operator machine, run from an **unelevated Windows 11 x64** PowerShell
session. The same check accepts the x64 Server 2025 API baseline used by CI,
records its actual build, and requires build 22000 or later:

```powershell
& $Exe check $Runtime $Pin $NewWorkRoot
if ($LASTEXITCODE -ne 0) { throw 'Native check failed; retain its diagnostics' }
```

All four arguments after the executable are literal CLI values: `check`, the
absolute extracted-runtime directory, the absolute `runtime-pin.json`, and a
**new absolute workroot whose parent already exists**. The probe creates the
private case directory itself with current-user + SYSTEM access. Do not repair
its ACLs or run it as administrator to bypass a rejection.

Success requires exit zero, one JSON receipt with `status: passed`, exact
`sourceHead`, `caller.elevated: false`, all four cases, and a `PASS` line.
The cases cover restricted launch/handle/pipe/QMP premises, parent death before
resume, parent death while the pipe is unconnected, and child-only owner-lock
retention. The receipt is measured by the executable, not generated by packaging.

This uses real QEMU with a fixed **no-VM qtest** invocation. qtest is not a WHPX
fallback. Tiny inert guest fixtures satisfy opaque input verification but are
never guest boot arguments: **guest assets are not qualified**. Neither a guest
boot nor WHPX usability is tested.

CI uses a new standard local user and the same CLI, with no inherited step-token
environment. A credential/Secondary Logon failure or platform rejection fails
the run; there is no elevated fallback. Hosted `windows-2025` is Server 2025,
not a Windows 11 client: its actual OS metadata and the probe's acceptance or
rejection must be read from the result, not inferred from its runner label.
Before starting any workers, the executable assigns its own controller to a
noninherited kill-on-close Job. Controller exit or interruption then reaps the
test tree. The Job stays alive during each worker-death proof, so it cannot hide
a failed inner Job. The production QEMU launch remains the unchanged atomic
Job-list creation. CI gives the controller eight minutes, then kills only its
owned process handle
and exit observed for up to 45 seconds. The account is removed afterward.
Private case files are never made readable for upload; they disappear with the
hosted runner. An interrupted or unobserved teardown is not a pass.

## Operator artifact

The flat `bridge-windows-native-check-<driver-sha>-<attempt>` artifact lasts
**seven days**. It contains the unchanged runtime/source ZIPs and original
`SHA256SUMS`, the executable, pin, provenance, independent verification, and
actual CI diagnostics. `operator-sha256sums.txt` hashes only explicitly named
files that exist. Failure artifacts can be incomplete and are **not ready
bundles**. No release, private case directory, credentials, workspace, or
toolchain is uploaded.

Only after a successful run, use its **actual** run ID, artifact name and
reviewed checksum evidence. No native-check run ID or digest is asserted here.
From PowerShell, an existing authenticated WSL GitHub login can download it:

```powershell
wsl.exe -- gh run download $RunId --repo orka-agents/orka-bridge --name $ArtifactName --dir $NewWslDestination
if ($LASTEXITCODE -ne 0) { throw 'Download failed' }
```

Use a new WSL destination mapped to a Windows directory (for example below
`/mnt/c/`). Check the selected run/head/conclusion and compare the executable
digest with the actual CI log. Verify every entry of
`operator-sha256sums.txt` and both original `SHA256SUMS` entries using
`Get-FileHash -Algorithm SHA256` before extracting the portable ZIP to a new
directory. Preserve the source ZIP and notices. Set `$Exe`, `$Runtime`,
`$Pin`, and `$NewWorkRoot` to those actual absolute paths, then run the CLI
above. A local pass supplements CI; it does not qualify guest assets or WHPX.
